TAIXU PLUGIN GUIDE / SCHEMA 1

Bring your tools
into TaiXu.

Use an online registry or a self-contained .txplugin to bring commands, SDKs, scripts, and local services into the ARM64 Linux sandbox. This guide documents the actual constraints of the current importer and installer.

01 / Local and online plugins

SourceManifestAssets
Online pluginREMOTE + SCRIPTBuilt-in or signed registry
Local pluginLOCAL + LOCAL_PACKAGEImported by the user .txplugin

The importer forces local packages to be marked as source=LOCAL, offlineOnly=true, and installMethod=LOCAL_PACKAGE. If a local and online plugin share an ID, the local version takes precedence in the UI.

permissions is currently used for manifest validation and UI display; it is not a permission sandbox for install scripts. Plugin scripts can still modify any path writable by the current user inside PRoot.

02 / Plugin package format

Local plugins use a ZIP container with the .txplugin extension. The root must directly contain manifest.json and payload/.

hello-arm64.txplugin
├── manifest.json
└── payload/
    ├── archives/       # SDK, NDK, Flutter, and other archives
    ├── scripts/        # Install, verification, and uninstall scripts
    ├── config/         # Configuration templates
    └── bin/            # ARM64 files
  • Only manifest.json and payload/ are allowed; absolute paths and .. are forbidden.
  • manifest.json is limited to 1 MiB.
  • Total uncompressed content is limited to 8 GiB.
  • Before installation, the payload is copied to /opt/taixu/imports/<id>.

03 / Writing manifest.json

{
  "schemaVersion": 1,
  "id": "hello-arm64",
  "name": "Hello ARM64",
  "description": "TaiXu local plugin example",
  "version": "1.0.0",
  "publisher": "Your Name",
  "category": "DEVELOPER",
  "launchType": "command",
  "architectures": ["ARM64"],
  "permissions": [],
  "source": "LOCAL",
  "offlineOnly": true,
  "installMethod": "LOCAL_PACKAGE",
  "launchCommand": "hello",
  "verifyCommand": "hello",
  "commandLinks": ["hello"]
}
FieldCurrent constraints
idLowercase letters, digits, and hyphens; length 2–64.
versionMust not be empty; the recommended format is x.y.z.
launchTypeone_shot, command, pty, web, or service.
architecturesMust include ARM64.
permissionsNETWORK, WORKSPACE_READ, WORKSPACE_WRITE, LOCAL_WEB.
commandLinksLinks by default to $TAIXU_TOOL_DIR/bin/<command>.

04 / Create a Hello plugin from scratch

Place the script at payload/bin/hello：

#!/bin/sh
echo "hello from TaiXu"

The install step must create the tool directory and restore executable permissions:

"installSteps": [
  "test -f \"$TAIXU_PLUGIN_PAYLOAD/bin/hello\"",
  "mkdir -p \"$TAIXU_TOOL_DIR/bin\"",
  "cp \"$TAIXU_PLUGIN_PAYLOAD/bin/hello\" \"$TAIXU_TOOL_DIR/bin/hello\"",
  "chmod 755 \"$TAIXU_TOOL_DIR/bin/hello\""
]

The installer provides TAIXU_TOOL_ID, TAIXU_TOOL_DIR, TAIXU_TOOL_DATA, and TAIXU_PLUGIN_PAYLOAD for local plugins.

05 / Packaging, versions, and quick updates

Windows PowerShell

Compress-Archive `
  -LiteralPath .\hello-arm64\manifest.json, .\hello-arm64\payload `
  -DestinationPath .\hello-arm64.zip -Force
Move-Item .\hello-arm64.zip .\hello-arm64.txplugin

Linux / macOS

cd hello-arm64
zip -r ../hello-arm64.txplugin manifest.json payload

Use a Zip64-capable tool for large plugins. For already-compressed .zip, .tar.gz, and .deb entries, prefer Store/NoCompression.

.txplugin is a ZIP file. When updating only the manifest or scripts, copy the old package and replace a few ZIP entries instead of unpacking and recompressing large archives. Reprocess large files only when replacing archives or changing compression formats.

  • The same id + version is reported as already imported and is not unpacked or installed again.
  • Different versions of the same ID can currently coexist.
  • Version directories are sorted lexicographically, not by full SemVer; until this is fixed, avoid using 1.0.9 and 1.0.10 together.
  • After you confirm a new package, the UI imports and installs it in sequence.

06 / Minimal RootFS and large dependencies

Do not assume the system includes unzip, xz, file, readelf, jq, Python, or Node. Prefer .tar.gz and verify archives with SHA-256.

archive="$TAIXU_PLUGIN_PAYLOAD/archives/flutter-arm64.tar.gz"
test -s "$archive"
printf '%s  %s\n' "<SHA256>" "$archive" | sha256sum -c -
rm -rf /opt/flutter.staging
mkdir -p /opt/flutter.staging
tar -xzf "$archive" -C /opt/flutter.staging

AArch64 checks without relying on file or readelf:

elf_bytes() { od -An -t x1 "$@" 2>/dev/null | tr -d ' \n'; }
is_aarch64_elf() {
  test "$(elf_bytes -j 18 -N 2 "$1")" = "b700"
}
  • After extracting a ZIP, explicitly run chmod.
  • When finding tools that may be symlinks, use \( -type f -o -type l \).
  • Do not pass a glob that may expand to multiple paths directly to test -x.
  • The same ARM64 architecture does not imply ABI compatibility between Android/Bionic and Linux/glibc.

07 / Live progress and install logs

Plugin scripts can emit monotonically increasing structured relative progress, which the app maps to the full installation progress bar:

[TAIXU_PROGRESS:47] [EXTRACT] Extracting Android NDK r29
[TAIXU_PROGRESS:75] [COMMAND] Configuring ADB
[TAIXU_PROGRESS:98] [VERIFY] Running final verification

Recommended labels are [COPY], [EXTRACT], [COMMAND], and [VERIFY]. Do not enable set -x, because it may write tokens, proxy details, or environment variables to logs.

08 / Timeouts, storage, and rollback boundaries

  • Install scripts time out after 15 minutes by default; verification commands after 60 seconds.
  • Large packages need space for the private plugin copy, sandbox payload copy, staging area, and final directory.
  • Framework transactions snapshot only /opt/taixu/tools/<id>.
  • /opt/android-sdk, /opt/flutter, /root/.gradle, and other global paths must be staged and cleaned up by the plugin itself.
  • A ROLLED_BACK log entry does not mean every global file has been restored.
  • verifyCommand must return 0; do not rely on legacy compatibility command fallbacks.

09 / Pre-release checklist

  • The ZIP root layout, 1 MiB manifest limit, and 8 GiB unpacked-size limit are satisfied.
  • Local/online source, ID, version, ARM64 architecture, launch type, and permission fields are correct.
  • Every large file has a pinned SHA-256.
  • No undeclared optional commands such as unzip, xz, file, or readelf are required.
  • ELF files, symlinks, and ZIP executable bits are handled.
  • Import, install, validation, and launch work offline.
  • Fresh install, duplicate import, upgrade, and uninstall are all tested.
  • Structured progress is monotonic, and logs contain no sensitive information.
  • Staging can be cleaned after failure, and all disk copies have been accounted for.
